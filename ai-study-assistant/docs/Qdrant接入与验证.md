# Qdrant 接入与验证

## 数据流

MySQL 仍保存笔记及片段，是归属和内容的权威来源。笔记修改、删除或片段重建时，同一个 MySQL 事务登记 Qdrant 同步任务；后台执行者逐条领取、写入或删除 Qdrant。失败后最多自动尝试 3 次，相邻失败默认等待 30 秒；耗尽后可以通过本人接口手动重试。

检索开启 Qdrant 时，先检查本用户的片段是否都已同步且模型一致，并对比 MySQL 与 Qdrant 中该用户的片段总数；检索结果再逐条回 MySQL 验证所属用户、片段和正文。存在未同步、数量不一致、无结果、连接异常或内容异常时回退现有 MySQL 搜索。精确计数和回查会增加查询开销；索引结果和 MySQL 的语义得分可能不同。即使总数相同也不能证明两边记录完全一致，因此这不是强一致性保证。

## 运行与旧数据回填

1. 启动 MySQL、Ollama 和 Qdrant。项目使用 `study_note_chunks_v1`，维度 1024，Cosine；确认 Qdrant 数据已经持久化并定期备份。项目使用 `qwen3-embedding:0.6b`；更换模型后必须重新构建数据库片段和索引，不能混用。
2. 已有数据库需先按顺序执行尚未执行的 `004_note_vector_sync_tasks.sql`、`005_note_vector_sync_retry.sql`。在 IDEA 中刷新 Maven 依赖并重启应用。
3. 登录后可执行 `http/Qdrant同步示例.http` 中的批量回填。它只安排当前用户有片段且还没有任务的笔记，不覆盖已有任务。回填会调用本地 Ollama 重新计算向量，数量多时需要时间。
4. 使用单篇状态接口查看 PENDING、RUNNING、SUCCEEDED、FAILED；FAILED 可等待重试，3 次失败后可以手动调用 retry。备份和还原集合后需要重新登记索引或进行对账。

配置 `QDRANT_SYNC_ENABLED=false` 可暂停后台处理，`QDRANT_SEARCH_ENABLED=false` 可切回 MySQL 搜索。切换前应确认没有旧工作进程还在操作同一集合。

## 重要边界

- MySQL 和 Qdrant 不能共用一个事务。重建时先删除旧向量再逐条写入，可能暂时缺失或部分写入；状态未完成时检索回退 MySQL。新数据更改会登记新版本，旧任务完成后新版本重新排队。
- 进程中断、数据库连接中断或状态更新失败可能使任务停在 RUNNING。不能只凭超时自动恢复：旧进程可能仍在写入 Qdrant。先停止所有可能处理任务的应用进程，再按 `Qdrant任务手动恢复.md` 检查令牌并手动处理。没有自动租约或分布式写入隔离。
- userId 和 noteId 由已验证身份的后端传入；结果仍通过 MySQL 校验。不要把无鉴权的 Qdrant 服务暴露到公网。
- Qdrant 原生点位被第三方修改或删除、迁移不同模型、嵌入向量被更改时需要对账和重建；当前并非生产级强一致性方案。
- 返回 top 10 的排序/答案依赖模型、数据和 Qdrant 索引。小样本结果不代表准确率保证；需要使用自己的资料评估召回、耗时和资源占用。
